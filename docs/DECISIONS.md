# 設計判断の記録

> **このドキュメントの位置づけ**
> 実装から導けない判断（**なぜ**その構造にしたか）だけを記録する。構造・スキーマ・API・型階層の「現状」は実装が正であり（Flyway マイグレーション / 実クラス / ArchUnit・PMD・Checkstyle の強制ルール）、本書では再記述しない。
> 判断が覆ったときは該当項目を書き換える（履歴は git が持つ）。

---

## 1. ドメインIDとDB内部IDを分離する

**判断**: 集約・エンティティの識別子は UUIDv7 の文字列（ドメインID）とし、DBの主キー・外部キー・JOIN には別途 `Long` の自動採番（内部ID）を使う。ドメイン層・REST API・外部連携はドメインIDだけを使い、内部IDは永続化層の外へ出さない。

**なぜ**:
- ドメイン層をDBの採番機構から切り離せる（永続化前に識別子を確定できるため、生成とテストがDBに依存しない）
- 外部へ公開する識別子が連番にならない（件数や作成順が推測されない）
- 分散環境でも衝突なく生成できる

**なぜ UUIDv7 か**: 時系列でソート可能なため主キーインデックスの局所性が UUIDv4 より良く、生成側でタイムスタンプ順序が保証される。

**実体**: `domain/model/EntityId`（生成・形式検証）、`*TableRecord` の `domain_id` 列、`V13`/`V22`/`V25` マイグレーション。

## 2. 集約間はID参照にする

**判断**: 集約をまたぐ関連はドメインIDの参照だけを持ち、オブジェクト参照は持たない。DBの外部キー制約も集約間には張らない。

**なぜ**: トランザクション境界を集約単位に閉じ、片方の集約を読むために他方をロード・ロックしないようにする。集約間の整合はユースケース側（アプリケーション層）で明示的に扱う。

**トレードオフ**: DBが参照整合を保証しないため、参照先を削除するとダングリング参照が起こり得る。参照チェックはユースケースの責務として個別に設計する（Album 削除に伴う記事の参照は 12 の方針で整備済み。Tune 削除は #151）。

**実体**: `V14`（集約間のFK削除）、`Article.albumId` / `TrackTune.tuneId` などのID参照。

## 3. Album 集約に Track / TrackTune を含める

**判断**: Track・TrackTune は独立集約にせず Album 集約内のエンティティとし、Album 集約を単位に永続化する。

**なぜ**: 「アルバムのトラック構成」は一貫性を1トランザクションで守りたい単位そのものであり、1アルバムのトラック数は通常10〜20曲程度で集約サイズが問題にならない。

**見直し条件**: トラック数の増大やロック競合でパフォーマンス問題が出た場合、Track を別集約へ分離する。

**実体**: `domain/model/aggregate/album/`（Album / Track / TrackTune）、`AlbumRepository` のみ存在すること。

## 4. ArtistCredit とイベント頒布情報を集約ルートにせずVO埋め込みにする

**判断**: アーティスト名義（`ArtistCredit`）とイベント頒布情報（`EventReleasedAt`）は独立集約ルートにせず、`Album` / `Track` に埋め込む値オブジェクトとして扱う。`Album` では名義必須、`Track` では nullable（null なら Album の名義を継承）。

**なぜ**: いずれも表示名・ソートキー程度の単純構造で独自のライフサイクルやロジックを持たず、常に Album / Track から従属的に参照される。集約ルートにすると Repository / DataSource / Mapper と JOIN が増えるだけで、得るものがない。

**トレードオフ**:
- 同一アーティスト名が複数アルバムに重複保存される（この規模では許容する）
- 名義やイベントに独自ロジックが必要になれば集約ルートへ分離しうる

**実体**: `domain/model/vo/common/ArtistCredit` / `EventReleasedAt`、`V15`/`V16`/`V17`（テーブルから埋め込みへの移行）。

## 5. 全テーブルに共通監査列7列を置く

**判断**: すべてのテーブルに `created_at` / `updated_at` / `created_by_service` / `updated_by_service` / `created_by_user` / `updated_by_user` / `version` を持たせる。

**運用ルール**:
- `created_at` / `updated_at` はDBのDEFAULTに任せ、アプリケーションから明示的に設定しない
- 業務的に意味を持つ日時（公開日時など）は監査列と混ぜず別カラムに持つ
- ユーザーIDは外部サービスのIDを想定して `VARCHAR`
- 楽観ロックはJPAの `@Version`（`version` 列）

**なぜ**: 監査証跡と楽観ロックを、テーブルごとの設計判断にせず一律で持たせるため。業務日時を監査列に兼用すると「レコードの更新」と「業務上の変更」が区別できなくなるため分ける。

**実体**: `infrastructure/persistence/entity/AuditableTableRecord`、`V12`（既存テーブルへの追加）。

## 6. 録音・チューンのモデリング

**判断**:
- Track は**録音単位**とし、同じ曲の録音違いは別 Track として扱う
- 1 Track に 0..n 個のチューン（曲）が順序付きで紐づく（1トラックに複数曲のセットを収録できる）
- Tune はトラッド／オリジナル／アレンジを区別し、アレンジの原曲は**テキスト情報として持つ**（原曲そのものをレコードにしない）
- クレジット（作曲者・アレンジャー）は Tune 側の既定値を持ち、TrackTune で上書きできる
- 外部サイトへのリンクはURL文字列1本で扱い、リンク先種別ごとの多態な参照にしない

**なぜ**: 伝統曲を含むリリースでは「曲」のマスタを厳密に管理するコストに見合う利益がない（原曲マスタを持つと出典の同一性判定という別問題を抱える）。セット曲・録音違いは実際のリリース形態としてありふれているため、モデルの一級市民として扱う。

**実体**: `domain/model/aggregate/album/Track` / `TrackTune`、`domain/model/aggregate/tune/Tune`、`V4`〜`V6`。

## 7. 音源は自前配信せず外部サービスの埋め込みに委ねる

**判断**: 画像アセットは自前でアップロード・配信する（`/assets/*`）が、音源は自前ホストせず外部サービス（SoundCloud）の埋め込みに委ねる。

**なぜ**: 音源は1ファイル数十MB〜500MB規模になり、CloudFrontの転送費が再生数に比例して読めない（500MBを100回フル再生で約$5.7、1,000回で約$57）。保管費（S3、数GBで月$0.2未満）は問題にならないが、転送費は個人運用のコスト構造で唯一効く変動費になる。

**トレードオフ**: 外部サービスの可用性・UI・埋め込み仕様に依存する。CSPの `frame-src` 許可が必要になる。自前配信へ戻す場合はアップロード基盤の上限と許可形式を足すだけで済むよう、アップロード経路は署名付きURL方式で統一している。

**実体**: `application/service/asset/`（画像専用の受け入れ形式）、`domain/model/vo/common/AssetKey` と対になる `ExternalAudioUrl`（埋め込み可能なホストの許可リスト）、`V32`（Albumの外部音源）。公開サイト側の埋め込み表示とCSPは #155。

## 8. プラットフォームは「上流の対応範囲内かつ保守されている系列」に置く

**判断**: Java（Amazon Corretto）・Quarkus・Gradle は固定して運用するが、固定の条件は「上流が対応を表明する範囲内であり、かつ保守されている系列であること」。この条件を外れたら昇格する。

**なぜ**: 当初の固定は「スキャフォールド当日の最新版」で、Java 25 の採用が Quarkus 側の対応（対応JVM 17–25 を表明したのは 3.32.0）より先行していた。結果として、保守が止まった系列（3.28 系は 3.28.5 で以後リリースなし）で、かつ上流が対応表明していない JDK 組み合わせを固定し続ける状態になっていた。「固定して安定を買う」意図が「パッチもサポートも受けられない状態を維持する」に反転していたため、固定の条件を明文化する。

**昇格時の作法**: Quarkus 本体・quarkiverse 拡張・AWS SDK・ErrorProne + NullAway は相互に噛み合うため、まとめて1つの変更として上げる。検証は `check`（静的解析・単体・実DB統合テスト）→ `quarkusBuild`（uber-jar）→ コンテナイメージビルドまで通す。

**個別の固定理由**（詳細は `build.gradle` のコメントが正）:
- quarkiverse 拡張は Quarkus 本体と別リリース列で、各版が特定の Quarkus 版を前提にビルドされる。本体を上げるときに揃える
- NullAway は ErrorProne の内部APIに密結合するため、NullAway が前提とする ErrorProne 版と対で上げる

**トレードオフ**: 追従の手間が定期的に発生する。自動化と追従頻度の方針は #158 で扱う。

## 9. アセットは配信URLではなく保管キーを保存する

**判断**: 集約が持つのはアセットの保管キー（`AssetKey`）であり、配信URLは照会時に配信ベースパスと組み合わせて Read Model 側で組み立てる。登録・更新APIはキーを受け取り、照会APIはURLを返す。

**なぜ**: 配信URLを保存すると、CDNのパス構成変更やドメインの差異（ローカル/本番）で保存データが無効になる。また実際のドメイン名をDBに持ち込まない方針とも整合する。OG画像など絶対URLが必要な用途は、公開サイトが自身のサイトURL設定から組み立てられる。

**実体**: `domain/model/vo/common/AssetKey`、`application/query/album/AlbumViewMapper`、`abservice.assets.public-base-path`。

## 10. 観測性はアプリ固有の実装を持たず拡張の標準経路に載せる

**判断**: ヘルスチェックは自前のリソースクラスを持たず `quarkus-smallrye-health` の `/q/health/{live,ready}` に委ね、readiness のDB接続確認も datasource 拡張の自動登録に任せる。メトリクスは micrometer が `/q/metrics` に Prometheus 形式で公開する。いずれも `/q/*` のため本番で外部から到達しない。ログは prod のみ JSON（1レコード1行）で標準出力へ出す。

**なぜ**: 手書きの `/api/v1/health` は固定文字列を返すだけで、依存先が落ちても UP を返す（＝監視として機能しない）状態だった。拡張の自動登録に載せれば、データソースを増やしたときも検査対象が追随する。公開APIのパス（`/api/v1/**`）に監視用のエンドポイントを混ぜないことで、CloudFront が backend へ流す経路を `/api/*` に限ったまま監視を内側に閉じられる。ログのJSON化を prod 限定にするのは、収集側（CloudWatch Logs）が構造化を求める一方、開発中はプレーン出力の可読性が要るため。

**トレードオフ**: 監視は稼働環境の内側からの到達を前提にする（外部からの合成監視には公開エンドポイントを使う）。収集・アラームはAWS設定を要するため #168 で扱う。

**実体**: `build.gradle`（`quarkus-smallrye-health` / `quarkus-micrometer-registry-prometheus` / `quarkus-logging-json`）、`application.properties`（`%prod` のログ形式）、`docker-compose.prod.yml`（readiness を使う healthcheck）。

## 11. 一覧の並び順はフロントが指定し、バックエンドは中立な既定と閉じた選択肢だけを持つ

**判断**: 一覧照会の並び順はクエリパラメータで選ぶ。許可値は集約ごとの列挙で閉じ、要求元（公開向け／管理向け）で集合を分ける。未指定時の既定は `domainId` 降順（登録の新しい順）とし、リリース日か公開日時かという意味づけを既定へ埋め込まない。同値時のタイブレークには常に `domainId` を第1キーと同じ向きで加える。

**なぜ**: 「何を新着と呼ぶか」はサイト側の編集判断であり、APIの既定に埋めると表示要件が変わるたびに契約が動く。バックエンドは選べる並びの提供に留め、意味のある並びは画面が明示する。許可値を列挙で閉じるのは、内部のプロパティ名を外部へ露出させず、`Sort` へ渡す文字列を外部入力にしないため。タイブレークが必要なのは、同値が並ぶとページネーションで行の重複・欠落が起きるため。`domainId` は UUIDv7 で一意かつ時系列順なので、タイブレークと中立な既定を兼ねられる。

**トレードオフ**: 画面側が常に並び順を指定する必要がある（既定に頼ると登録順になる）。値を持たない行の位置は向きに依らず末尾に固定するため、降順で null を先に見たい要求には応えられない。

**実体**: `application/query/SortKey` / `SortKeys` / `SortSpec` / `SortDirection`、集約ごとの `*SortKey`、`infrastructure/persistence/datasource/SortOrders`。

## 12. 参照先を失った参照は「失効」として型に残す

**判断**: Album は物理削除する（論理削除や削除済みアルバムテーブルは持たない）。参照していた Article は残し、参照を「失効」状態へ遷移させる。失効した参照は旧アルバムID・失効日時・理由コードを保持し、参照の状態（なし / 有効 / 失効）は sealed 型で判別する。削除時、公開中だった記事は同一トランザクションで非公開へ戻し、影響を受けた記事を応答に含める。失効した参照を持つアルバム記事は公開できない。記事種別（`ArticleType`）はシステムから変更しない。

**なぜ**: 削除済みを別テーブルへ退避すると実質的に論理削除になり、公開判定と参照解決が二重になる。一方で参照を単に null へ戻すと「なぜ参照が無いのか」が失われ、編集者が張り直しの判断をできない。状態を型で持てば、公開ユースケースの分岐が網羅性検査の対象になり、「参照先のない公開記事」を作る経路が構造的に閉じる。種別を書き換えないのは、種別が人の記述であってシステムの推論結果ではないため（#89 の区別と同じ趣旨）。

**トレードオフ**: 失効情報は1件しか持たないため、同じ記事が複数回参照を失うと直前の経緯だけが残る。横断的な「システムからのお知らせ」を持つ仕組み（#174）を入れるなら、そこへ移す判断があり得る。

**実体**: `domain/model/vo/article/AlbumReference`（sealed）と `AlbumReferenceLostReason`、`application/service/album/DeleteAlbumService`、`application/service/article/PublishArticleService`、`V33`。
