# 設計判断の記録

> **このドキュメントの位置づけ**
> 実装から導けない判断（**なぜ**その構造にしたか）だけを記録する。構造・スキーマ・API・型階層の「現状」は実装が正であり（Flyway マイグレーション / 実クラス / ArchUnit・PMD・Checkstyle の強制ルール）、本書では再記述しない。
> 判断が覆ったときは該当項目を書き換える（履歴は git が持つ）。

## 1. ドメインIDとDB内部IDを分離する

**判断**: 集約・エンティティの識別子は UUIDv7 の文字列（ドメインID）とし、DBの主キー・外部キー・JOIN には別途 `Long` の自動採番（内部ID）を使う。ドメイン層・REST API・外部連携はドメインIDだけを使い、内部IDは永続化層の外へ出さない。

**なぜ**:
- ドメイン層をDBの採番機構から切り離せる（永続化前に識別子を確定できるため、生成とテストがDBに依存しない）
- 外部へ公開する識別子が連番にならない（件数や作成順が推測されない）
- 分散環境でも衝突なく生成できる

**なぜ UUIDv7 か**: 時系列でソート可能なため主キーインデックスの局所性が UUIDv4 より良く、生成側でタイムスタンプ順序が保証される。

**実体**: `domain/model/EntityId`（生成・形式検証）、`*TableRecord` の `domain_id` 列、`V13`/`V22`/`V25` マイグレーション。

## 2. 集約間はID参照にする

**判断**: 集約をまたぐ関連はドメインIDの参照だけを持ち、オブジェクト参照は持たない。DBの外部キー制約も集約間には張らない。

**なぜ**: トランザクション境界を集約単位に閉じ、片方の集約を読むために他方をロード・ロックしないようにする。集約間の整合はユースケース側（アプリケーション層）で明示的に扱う。

**トレードオフ**: DBが参照整合を保証しないため、参照先を削除するとダングリング参照が起こり得る。参照チェックはユースケースの責務として個別に設計する（Album 削除に伴う記事の参照は 12 の方針で整備済み。Tune 削除は #151）。

**実体**: `V14`（集約間のFK削除）、`AlbumArticle.albumReference` / `TrackTune.tuneId` などのID参照。

## 3. Album 集約に Track / TrackTune を含める

**判断**: Track・TrackTune は独立集約にせず Album 集約内のエンティティとし、Album 集約を単位に永続化する。

**なぜ**: 「アルバムのトラック構成」は一貫性を1トランザクションで守りたい単位そのものであり、1アルバムのトラック数は通常10〜20曲程度で集約サイズが問題にならない。

**見直し条件**: トラック数の増大やロック競合でパフォーマンス問題が出た場合、Track を別集約へ分離する。

**実体**: `domain/model/aggregate/album/`（Album / Track / TrackTune）、`AlbumRepository` のみ存在すること。

## 4. ArtistCredit とイベント頒布情報を集約ルートにせずVO埋め込みにする

**判断**: アーティスト名義（`ArtistCredit`）とイベント頒布情報（`EventReleasedAt`）は独立集約ルートにせず、`Album` / `Track` に埋め込む値オブジェクトとして扱う。`Album` では名義必須、`Track` では nullable（null なら Album の名義を継承）。

**なぜ**: いずれも表示名・ソートキー程度の単純構造で独自のライフサイクルやロジックを持たず、常に Album / Track から従属的に参照される。集約ルートにすると Repository / DataSource / Mapper と JOIN が増えるだけで、得るものがない。

**トレードオフ**:
- 同一アーティスト名が複数アルバムに重複保存される（この規模では許容する）
- 名義やイベントに独自ロジックが必要になれば集約ルートへ分離しうる

**実体**: `domain/model/vo/common/ArtistCredit` / `EventReleasedAt`、`V15`/`V16`/`V17`（テーブルから埋め込みへの移行）。

## 5. 全テーブルに共通監査列7列を置く

**判断**: すべてのテーブルに `created_at` / `updated_at` / `created_by_service` / `updated_by_service` / `created_by_user` / `updated_by_user` / `version` を持たせる。

**運用ルール**:
- `created_at` / `updated_at` の時刻源はアプリケーション（JVM）。DBの `DEFAULT CURRENT_TIMESTAMP` は、マイグレーションのようにアプリケーションを経由しない挿入の保険として残す
- actor 4列（`*_by_service` / `*_by_user`）は**未特定のまま運用する**（NULL）。行ごとに区別できる actor を持つ認証を入れた時点で埋める
- 業務的に意味を持つ日時（公開日時など）は監査列と混ぜず別カラムに持つ
- 楽観ロックはJPAの `@Version`（`version` 列）

**なぜ**: 監査証跡と楽観ロックを、テーブルごとの設計判断にせず一律で持たせるため。業務日時を監査列に兼用すると「レコードの更新」と「業務上の変更」が区別できなくなるため分ける。

時刻源をアプリケーションに置くのは、`updated_at` をDB側で維持するには全テーブルにトリガが必要で、単一プロセスで書き込む構成では引き合わないため。挿入時にアプリが値を送るのでDBのDEFAULTは実際には適用されないが、経路が増えたときに NOT NULL 違反で落ちないよう残す。

actor 列を埋めないのは、現行の認証が単一の管理者を表す固定 principal しか発行せず、埋めても全行が同じ値になり「誰が」の情報を持たないため。定数を入れると、後から実際の識別子が入り始めたときに解釈の混ざった列になる。**この状態を「監査証跡が完成している」とは記述しない**（列の存在＝追跡できる、ではない）。

**トレードオフ**: リリース時点では「いつ」だけが追え、「誰が」は追えない。単一管理者の運用では実質的な損失は小さいが、複数の管理者を扱う時点で actor を埋める作業（認証側の識別子の決定と、書き込み経路への受け渡し）が必要になる。

**実体**: `infrastructure/persistence/AuditableTableRecord`（日時の設定と `@PreUpdate`）、`AuditInfo`（actor を埋める際の受け口。現時点で呼び出し元なし）、`V12`（既存テーブルへの追加）。

## 6. 録音・チューンのモデリング

**判断**:
- Track は**録音単位**とし、同じ曲の録音違いは別 Track として扱う
- 1 Track に 0..n 個のチューン（曲）が順序付きで紐づく（1トラックに複数曲のセットを収録できる）
- Tune はトラッド／オリジナル／アレンジを区別し、アレンジの原曲は**テキスト情報として持つ**（原曲そのものをレコードにしない）
- クレジット（作曲者・アレンジャー）は Tune 側の既定値を持ち、TrackTune で上書きできる
- 外部サイトへのリンクはURL文字列1本で扱い、リンク先種別ごとの多態な参照にしない

**なぜ**: 伝統曲を含むリリースでは「曲」のマスタを厳密に管理するコストに見合う利益がない（原曲マスタを持つと出典の同一性判定という別問題を抱える）。セット曲・録音違いは実際のリリース形態としてありふれているため、モデルの一級市民として扱う。

**実体**: `domain/model/aggregate/album/Track` / `TrackTune`、`domain/model/aggregate/tune/Tune`、`V4`〜`V6`。

## 7. 音源は自前配信せず外部サービスの埋め込みに委ねる

**判断**: 画像アセットは自前でアップロード・配信する（`/assets/*`）が、音源は自前ホストせず外部サービス（SoundCloud）の埋め込みに委ねる。

**なぜ**: 音源は1ファイル数十MB〜500MB規模になり、CloudFrontの転送費が再生数に比例して読めない（500MBを100回フル再生で約$5.7、1,000回で約$57）。保管費（S3、数GBで月$0.2未満）は問題にならないが、転送費は個人運用のコスト構造で唯一効く変動費になる。

**トレードオフ**: 外部サービスの可用性・UI・埋め込み仕様に依存する。CSPの `frame-src` 許可が必要になる。自前配信へ戻す場合はアップロード基盤の上限と許可形式を足すだけで済むよう、アップロード経路は署名付きURL方式で統一している。

**実体**: `application/service/asset/`（画像専用の受け入れ形式）、`domain/model/vo/common/AssetKey` と対になる `ExternalAudioUrl`（埋め込み可能なホストの許可リスト）、`V32`（Albumの外部音源）。公開サイト側の埋め込み表示とCSPは #155。

## 8. プラットフォームは「上流の対応範囲内かつ保守されている系列」に置く

**判断**: Java（Amazon Corretto）・Quarkus・Gradle は固定して運用するが、固定の条件は「上流が対応を表明する範囲内であり、かつ保守されている系列であること」。この条件を外れたら昇格する。

**なぜ**: 当初の固定は「スキャフォールド当日の最新版」で、Java 25 の採用が Quarkus 側の対応（対応JVM 17–25 を表明したのは 3.32.0）より先行していた。結果として、保守が止まった系列（3.28 系は 3.28.5 で以後リリースなし）で、かつ上流が対応表明していない JDK 組み合わせを固定し続ける状態になっていた。「固定して安定を買う」意図が「パッチもサポートも受けられない状態を維持する」に反転していたため、固定の条件を明文化する。

**昇格時の作法**: Quarkus 本体・quarkiverse 拡張・AWS SDK・ErrorProne + NullAway は相互に噛み合うため、まとめて1つの変更として上げる。検証は `check`（静的解析・単体・実DB統合テスト）→ `quarkusBuild`（uber-jar）→ コンテナイメージビルドまで通す。

**個別の固定理由**（詳細は `build.gradle` のコメントが正）:
- quarkiverse 拡張は Quarkus 本体と別リリース列で、各版が特定の Quarkus 版を前提にビルドされる。本体を上げるときに揃える
- NullAway は ErrorProne の内部APIに密結合するため、NullAway が前提とする ErrorProne 版と対で上げる

**トレードオフ**: 追従の手間が定期的に発生する。自動化と追従頻度の方針は #158 で扱う。

## 9. アセットは配信URLではなく保管キーを保存する

**判断**: 集約が持つのはアセットの保管キー（`AssetKey`）であり、配信URLは照会時に配信ベースパスと組み合わせて Read Model 側で組み立てる。登録・更新APIはキーを受け取り、照会APIはURLを返す。

**なぜ**: 配信URLを保存すると、CDNのパス構成変更やドメインの差異（ローカル/本番）で保存データが無効になる。また実際のドメイン名をDBに持ち込まない方針とも整合する。OG画像など絶対URLが必要な用途は、公開サイトが自身のサイトURL設定から組み立てられる。

**実体**: `domain/model/vo/common/AssetKey`、`application/query/album/AlbumViewMapper`、`abservice.assets.public-base-path`。

## 10. 観測性はアプリ固有の実装を持たず拡張の標準経路に載せる

**判断**: ヘルスチェックは自前のリソースクラスを持たず `quarkus-smallrye-health` の `/q/health/{live,ready}` に委ね、readiness のDB接続確認も datasource 拡張の自動登録に任せる。メトリクスは micrometer が `/q/metrics` に Prometheus 形式で公開する。いずれも `/q/*` のため本番で外部から到達しない。ログは prod のみ JSON（1レコード1行）で標準出力へ出す。

**なぜ**: 手書きの `/api/v1/health` は固定文字列を返すだけで、依存先が落ちても UP を返す（＝監視として機能しない）状態だった。拡張の自動登録に載せれば、データソースを増やしたときも検査対象が追随する。公開APIのパス（`/api/v1/**`）に監視用のエンドポイントを混ぜないことで、CloudFront が backend へ流す経路を `/api/*` に限ったまま監視を内側に閉じられる。ログのJSON化を prod 限定にするのは、収集側（CloudWatch Logs）が構造化を求める一方、開発中はプレーン出力の可読性が要るため。

**トレードオフ**: 監視は稼働環境の内側からの到達を前提にする（外部からの合成監視には公開エンドポイントを使う）。収集・アラームはAWS設定を要するため #168 で扱う。

**実体**: `build.gradle`（`quarkus-smallrye-health` / `quarkus-micrometer-registry-prometheus` / `quarkus-logging-json`）、`application.properties`（`%prod` のログ形式）、`docker-compose.prod.yml`（readiness を使う healthcheck）。

## 11. 一覧の並び順はフロントが指定し、バックエンドは中立な既定と閉じた選択肢だけを持つ

**判断**: 一覧照会の並び順はクエリパラメータで選ぶ。許可値は集約ごとの列挙で閉じ、要求元（公開向け／管理向け）で集合を分ける。未指定時の既定は `domainId` 降順（登録の新しい順）とし、リリース日か公開日時かという意味づけを既定へ埋め込まない。同値時のタイブレークには常に `domainId` を第1キーと同じ向きで加える。

**なぜ**: 「何を新着と呼ぶか」はサイト側の編集判断であり、APIの既定に埋めると表示要件が変わるたびに契約が動く。バックエンドは選べる並びの提供に留め、意味のある並びは画面が明示する。許可値を列挙で閉じるのは、内部のプロパティ名を外部へ露出させず、`Sort` へ渡す文字列を外部入力にしないため。タイブレークが必要なのは、同値が並ぶとページネーションで行の重複・欠落が起きるため。`domainId` は UUIDv7 で一意かつ時系列順なので、タイブレークと中立な既定を兼ねられる。

**トレードオフ**: 画面側が常に並び順を指定する必要がある（既定に頼ると登録順になる）。値を持たない行の位置は向きに依らず末尾に固定するため、降順で null を先に見たい要求には応えられない。

**実体**: `application/query/SortKey` / `SortKeys` / `SortSpec` / `SortDirection`、集約ごとの `*SortKey`、`infrastructure/persistence/datasource/SortOrders`。

## 12. 参照先を失った参照は「失効」として型に残す

**判断**: Album は物理削除する（論理削除や削除済みアルバムテーブルは持たない）。参照していた Article は残し、参照を「失効」状態へ遷移させる。失効した参照は旧アルバムID・失効日時・理由コードを保持し、参照の状態（なし / 有効 / 失効）は sealed 型で判別する。削除時、公開中だった記事は同一トランザクションで非公開へ戻し、影響を受けた記事を応答に含める。失効した参照を持つアルバム記事は公開できない。記事種別（`ArticleType`）はシステムから変更しない。

**なぜ**: 削除済みを別テーブルへ退避すると実質的に論理削除になり、公開判定と参照解決が二重になる。一方で参照を単に null へ戻すと「なぜ参照が無いのか」が失われ、編集者が張り直しの判断をできない。状態を型で持てば、公開ユースケースの分岐が網羅性検査の対象になり、「参照先のない公開記事」を作る経路が構造的に閉じる。種別を書き換えないのは、種別が人の記述であってシステムの推論結果ではないため（#89 の区別と同じ趣旨）。

**トレードオフ**: 失効情報は1件しか持たないため、同じ記事が複数回参照を失うと直前の経緯だけが残る。横断的な「システムからのお知らせ」を持つ仕組み（#174）を入れるなら、そこへ移す判断があり得る。

**実体**: `domain/model/vo/article/AlbumReference`（sealed）と `AlbumReferenceLostReason`、`domain/model/aggregate/article/AlbumArticle`（参照を持てる唯一の記事種別）、`application/service/album/DeleteAlbumService`、`application/service/article/PublishArticleService`、`V35`（`article_album_reference`）。

## 13. 集約をまたぐ操作は「試み」のオブジェクトにし、遷移を構造で閉じる

**判断**: 参照先集約の状態に依存する操作（記事の公開、記事へのアルバム紐付け）は、次の形で表す。

- **操作オブジェクト**: 参照先を伴って構築され、規則の評価（`asValidated`）と、規則を満たすときだけの遷移を自身が持つ。規則は値だけで評価できる `Policy` としてその内側に閉じる
- **置き場所**: 操作オブジェクトはドメインサービスのネスト型。永続化されず識別子も持たない、そのサービスの中でだけ意味を持つアドホックなモデルであり、集約・VO と同じ場所には置かない
- **ドメインサービス**: 参照先を引き（I/O）、操作オブジェクトを組み立てて実行する。操作ごとに1サービスとし、名前と操作を1対1にする
- **強制**: 遷移メソッドに `@CrossAggregateTransition`、操作オブジェクトに `@CrossAggregateOperation` を付け、遷移が操作オブジェクト以外から呼ばれないことを ArchUnit で検査する（呼び出しとメソッド参照の両方）
- コマンドサービスは取得・保存・出力の合成に徹し、「検証してから遷移を呼ぶ」順序の知識を持たない

**なぜ**: 検証と遷移が別々の呼び出しだと、順序を守るのは呼び出し側の規律に依存し、別のユースケースが遷移だけを呼べば不変条件が素通りする。参照先を渡さなければ操作オブジェクトを構築できない形にすれば、「参照先を見ずに遷移する」経路が構築の時点で存在しなくなる。規則を I/O から分離すると、判定は Uni にも DB にも依存せず単体で評価でき、照会側から「公開できる状態か」を問うような再利用にも開ける。ドメインサービスを操作ごとに分けるのは、1サービスに複数の操作を持たせると名前が実体を説明しなくなるため。

**トレードオフ**: 操作ごとにサービスとネスト型が増える。参照先を引く数行は各サービスに重複する（共有したい手順が3箇所目に現れた時点で括り出す）。ArchUnit の検査はアノテーションの付け忘れを検出できないため、新しい「参照先に依存する遷移」を追加する際は付与が要る。

**実体**: `domain/service/ArticlePublicationService`（`ArticlePublication`）、`domain/service/ArticleAlbumAttachmentService`（`AlbumAttachment`）、`domain/model/CrossAggregateTransition` と `CrossAggregateOperation`、`architecture/AggregateConstructionArchTest`。

## 14. アルバムを参照する記事は 0..N 件とする

**判断**: 1つのアルバムは複数の記事から参照されうる。参照先アルバムIDに一意制約は張らず、紐付け時にも「そのアルバムを参照する記事が他に無いこと」を求めない。アルバムの非公開化・削除に伴うカスケード（12）は、参照しているすべての記事へ適用する。

**なぜ**: 記事はアルバムから独立したライフサイクルを持ち（12）、参照は記事がアルバムを話題にするという片方向の関係でしかない。同じアルバムについて告知と振り返りのように複数の記事を書くことを禁じる業務上の理由がない。「1アルバムにつき代表記事1件」を出したい要求は、参照の多重度ではなく表示側の選択で解ける。多重度を 0..1 にすると、記事を書き足すたびに既存記事の参照を外すことになり、外された側は理由のない失効参照を持つ。

**トレードオフ**: 参照件数に上限がないため、カスケードの対象件数はアルバムごとに不定になる。同一トランザクション内で逐次保存するため、参照が極端に増えれば非公開化・削除の応答時間が伸びる。想定する規模では問題にならないが、増えるなら一括更新を検討する。

**実体**: `ArticleRepository.findByAlbumId`（リスト取得）、`application/service/album/UnpublishAlbumService` と `DeleteAlbumService` のカスケード、`V35`（`article_album_reference.album_id` は索引のみで一意制約を持たない。一意なのは記事ごとの参照が0..1件であることだけ）。

## 15. アルバムの取得は主張を伴い、主張は行の排他で表す

**判断**: アルバムを取得する側は、次のいずれかを主張する。

- **編集権**: 自分がそのアルバムを書き換える（公開・非公開・更新・トラック操作・削除）
- **参照**: アルバム自体は書き換えないが、その状態に依拠して別の集約を書き換える（記事の公開、記事へのアルバム紐付け）

主張はアルバム行の排他ロックとして実装し、呼び出し元のトランザクションがコミットするまで保持する。取得の口は `AlbumAccessService` の3メソッド（`findExistingAndClaimEdit` / `findExistingAndClaimReference` / `findAndClaimEditIfPresent`）に限り、主張を伴わない取得を業務コードから呼ばないことを ArchUnit で検査する。全経路が「アルバムを取得してから記事を書き換える」順になるため、ロック順序は Album → Article に固定される。

**なぜ**: 集約間はID参照でDBの外部キーも張らない（2）ため、「公開中の記事が非公開・削除済みのアルバムを参照しない」という集約をまたぐ不変条件は、判定に使ったアルバムが書き込みまでの間に動かないことに依存する。READ COMMITTED の read-check-write だけではこれを満たさず、行ごとの `@Version`（5）は同じ行の競合しか見ないため、別集約の行をまたぐ競合を検出できない。取得の口を1つに閉じ、その口が必ずロックを取る形にすれば、参照先に依存する操作が増えても主張の取り忘れが構造的に起きにくい。主張の種類を名前で分けるのは、呼び出し側のコードから「何を要求してこの取得をしたのか」が読めるようにするため（実装は共通で、名前だけが意図を運ぶ）。

**トレードオフ**: 同一アルバムを対象とする操作は直列化する。単一の管理者が誤って2画面から編集する程度の競合しか想定しないため、待ちがスループットの問題になることはない。集約のロードは `LEFT JOIN FETCH` を伴い、外部結合のnullable側に `FOR UPDATE` を適用できないため、ロックの取得は結合を伴わない別クエリになり、取得は2クエリになる。参照の主張も排他で表すため、記事の公開中はアルバムの編集が待たされる（共有ロックで緩められるが、競合しない前提では区別する利益がない）。

**実体**: `domain/service/AlbumAccessService`、`AlbumRepository#findByIdExclusively`、`AlbumDataSource#lockByDomainId`、`architecture/LayeredArchitectureTest#albumShouldOnlyBeObtainedThroughAClaim`。

## 16. 本番へ出せるのはCIが成功したcommitだけとする

**判断**: デプロイは main への push を直接のトリガーにせず、CI の完了を受けて起動し、対象を**そのCIが検査したSHA**へ固定する。手動起動は既存イメージの再デプロイ（ロールバック）に限り、タグの指定を必須にする。CIとデプロイを1つのワークフローへ統合する形は採らない。

**なぜ**: トリガーが独立していると、CIが失敗するcommitでもデプロイが先に完了しうる。SHAを固定するのは、CI完了後に main が進んでいた場合に「検査していないcommitを出す」ことを避けるため。手動起動から任意のcommitをビルドできると、そこが検査を通らない抜け道として残るため、手動経路は既存イメージの差し替えだけに閉じる。

統合しないのは、CIの並行制御が「同一ブランチの古い実行を打ち切る」形であり、同じワークフローに乗せると連続pushでデプロイ中の実行が打ち切られうるため。ジョブ単位で並行制御を分ければ回避できるが、打ち切ってよい処理と打ち切ってはならない処理を同じ実行単位に同居させること自体を避ける。

**トレードオフ**: CIの完了を受けて起動する形はデフォルトブランチ上の定義で実行されるため、デプロイ手順の変更は main に入るまで効かず、PR上では検証できない。またCIとデプロイが別実行になるため、デプロイの成否はCIの実行画面には現れない。

**実体**: `.github/workflows/deploy.yml`、`.github/workflows/ci.yml`、`infra/README.md`（運用手順）。

## 17. 参照されているチューンは削除させない

**判断**: トラック内のチューン構成から参照されているチューンは削除できない（ビジネスルール違反として拒否する）。参照を外す操作を先に要求する。参照側を null へ倒すカスケードは採らない。判定は参照の有無に依存しチューン集約単体では決まらないため、ドメインサービスが担う。

**なぜ**: チューンはアルバムから独立して存在する一方、参照はアルバム集約の内側にある。カスケードで参照を外すと「曲が不明な録音」というレコードが残り、それが業務上の記述（曲名が判らない録音）なのか削除の副作用なのかを区別できなくなる（#89 の「人の記述」と「システムの記述」を混ぜない趣旨）。アルバム削除（12）が参照を失効させる形を採るのは、アルバムが公開単位で削除が業務上の操作としてありうるのに対し、チューンの削除が例外的な整理作業であり、参照を外す判断を人に返せるため。

**トレードオフ**: 参照を持つチューンを消すには、先に各トラックの構成から外す必要がある。構成を編集する経路が無い間は、参照が付いたチューンは実質削除できない。

**実体**: `domain/service/TuneDeletionService`（`TuneDeletion`）、`AlbumRepository#existsTrackTuneReferencing`、`application/service/tune/DeleteTuneService`。

## 18. アセットの受け入れ前と配信対象を別の置き場に分ける

**判断**: 署名付きURLの宛先は受け入れ前の置き場（配信パスの外）とし、確定（confirm）で検査に通った実体を保管先の内部コピーで配信対象へ移す。配信対象のキーへ書き込める署名付きURLは発行しない。確定に至らなかった実体はライフサイクルで期限切れにする。

**なぜ**: 署名付きURLは一度発行すると有効期限内は何度でも使える（S3の署名は単回使用にできない）。配信キーへ直接アップロードさせると、確定で検査した実体と、その後にCDNが配信する実体が同一である保証が確定の瞬間に切れる。書き込める場所と配信される場所を分ければ、「確定した実体が配信される」が期限や運用の注意ではなく構造で決まる。受け入れ前を配信パスの外に置くのは、検査前・破棄予定の実体がCDNから到達しないようにするため。

**トレードオフ**: 確定のたびに保管先内のコピーが1回入る（実体はバックエンドを経由しないため転送費と待ち時間は保管先の内部に収まる）。受け入れ前の実体が一時的に二重に存在し、放置分の掃除をライフサイクルに依存する。バージョン固定（同一キーのまま検査したバージョンを配信する）でも同じ不変性は作れるが、バージョンIDを集約が保持することになり「集約が持つのは保管キー、配信URLは組み立てる」（9）とDBスキーマに影響が及ぶため採らない。

**実体**: `application/port/AssetStorage`（`presignUpload` / `publish` / `discard`）、`infrastructure/storage/S3AssetStorage`、`abservice.assets.pending-prefix`、`infra/data.tf`（`pending/` のライフサイクル）。

## 19. 作品の説明は Album が持ち、記事が語ることとは別に置く

**判断**: 作品そのものを説明する文章（概要説明）は `Album` が1つ持つ。記事が書く文章（頒布の告知、制作の経緯など）とは別の項目として扱い、一方を他方で代替しない。概要説明は公開制御に関与しない（カバー画像と同じく、未記入でも公開できる）。

**なぜ**: 公開アルバムページは作品の事実詳細をまとめるストック情報であり、記事は特定の時点について語るフロー情報である。同じ「アルバムの説明文」に見えても、前者は作品につき1つで作品が存在する限り妥当であり続けるのに対し、後者は作品につきN件あって書かれた時点の文脈に属する。両者を1箇所にまとめると、作品ページに出すべき説明を複数の記事から選び直す判断が毎回発生し、記事を書き足すたびに作品の説明が揺れる。

マークアップ形式を記事本文と同じ `MarkupContent` に揃えるのは、説明の表現力に差を設ける理由がないため。形式の解釈（レンダリング）はどちらもプレゼンテーション層の責務で、保存側は形式情報を持つ生のテキストに留まる。

**トレードオフ**: 説明が2種類存在するため、管理画面は「作品の説明」と「記事の本文」を書き分ける必要がある。書き分けの指針は画面側の文言で示す。

**実体**: `domain/model/aggregate/album/Album` の `description`、`domain/model/vo/common/MarkupContent`、`V34`。記事側の文章は `Article` の `body`。

## 20. 項目が無いことの表し方を、値の不在と型の不在で分ける

**判断**: 項目の値が無いことを表すときはキーを出して `null` を返し、その種別がその項目の概念を持たないときは**項目名自体を出さない**。後者はレスポンス型を分けることで実現し、`@JsonInclude(NON_NULL)` のような一律の null 除去は採らない。

「無い」ことがあり得ない項目は `null` を持たず、空を表す Null Object で表現する（本文は `MarkupContent.EMPTY`）。真に無いことがある項目（公開日時・業務上の更新日時）は `null` のままとする。

**なぜ**: 2種類の `null` が同じ形で現れると、クライアントは「値が未設定なのか、その種別には存在しない概念なのか」を区別できない。前者は表示上の空欄、後者は項目そのものを描画しないという別の扱いになる。一律の null 除去は両者を同じ「キーなし」へ潰すため、区別が失われる。

**トレードオフ**: 種別ごとにレスポンス型が分かれるため、クライアントは種別で分岐する。項目名の集合が同一の種別には別の型を与えない（`NOTE` / `NEWS` / `EVENT` / `OTHER` は1つの型が担う）ことで、型の数を項目名の違いの数に留める。

**実体**: `presentation/rest/article/response/ArticleResponse`（sealed）と `AlbumArticleResponse` / `PlainArticleResponse`、`domain/model/aggregate/article/ArticleCore` の `body`（非null）、`V36`。

## 21. 記事が指す作品は当面1件に限る

**判断**: 記事からアルバムへの参照は 0..1 件とし、中間テーブルを持たない。1つのアルバムが複数の記事から参照されること（14）は変えない。

**なぜ**: 本来、記事と作品は N対N である。1つのイベントで複数の新譜が出たり、準新譜を併せて紹介したりするお品書き記事は、複数の作品を指す。それを表すには中間テーブルと、記事が指す作品の集合を扱う操作が必要になる。

一方、複数の作品を1本の記事でまとめて扱う要求は「その発表（イベント）でどれを頒布したか」という単位から来ており、正しい受け皿は記事ではなく発表である。発表を第一級の概念にしないまま記事に集合を持たせると、記事がイベント単位のまとまりを代行することになり、発表という概念の不在を別の形で埋めることになる。発表の導入（#201）まで多重度を上げない。

**トレードオフ**: 1つのイベントで複数の作品を紹介する記事を、作品ごとに分けて書く運用になる。頒布情報・入手経路は本来（作品 × 発表）の組に属するため、この多重度のままでは正しい置き場がない。したがってそれらは実装せず、発表とセットで設計する（#201）。

**実体**: `domain/model/aggregate/article/AlbumArticle` の `albumReference`（単一）、`V35`（`article_album_reference` は `article_id` を主キーとし、1記事につき0..1件）。

## 22. 管理APIキーを localStorage に保持する

**判断**: 管理画面が使う管理APIキーはブラウザの `localStorage` に置く。キーを持たない状態で管理画面を開いたときは入力を求め、認証に失敗したら公開サイトのトップへ送る。

**なぜ**: 管理画面は同一利用者が複数のタブで並行して開く。タブごとに認証が切れる `sessionStorage` や、タブに閉じたメモリ上の保持では、タブを開くたびに入力を求めることになる。`localStorage` はオリジン単位で共有されるため、複数タブが同じキーを見る。

**この判断が前提にしていること**: `localStorage` は同一オリジンのスクリプトから読める。公開サイトと管理画面は単一ドメインのパス分岐（`/` と `/admin/*`）で配信されるため、**両者は同一オリジンであり、公開ページ側のXSSからも管理APIキーが読める**。それが許容できるのは、次の2つが成り立つ間に限られる。

- 公開ページが描画する文字列は、すべて管理者が入力したものである（利用者投稿・外部から取り込んだテキストを描画しない）
- 外部由来のコンテンツは埋め込みプレイヤーの iframe だけであり、これは別オリジンのため当サイトの `localStorage` を読めない

**したがって、公開ページが利用者投稿や外部由来のテキストを描画するようになった時点で、この判断を再評価する。** そのときは HttpOnly Cookie とサーバ側セッション、あるいはオリジンの分離を検討する。

**トレードオフ**: 上記の前提が崩れたことに気づかないまま公開ページの描画対象を広げると、キーの露出経路が生まれる。前提を本項に明記することでその検知を人手のレビューに委ねており、自動で守る手立て（描画経路の静的検査など）は持たない。

**実体**: `presentation/rest/security/ApiKeyIdentityProvider` と `abservice.auth.admin-api-key`（キーの検証側）、`infra/edge.tf`（`/` と `/admin/*` を同一ディストリビューションのパス分岐で配信する）。管理画面側の保持と入力は #164 のジャーニーで扱う。
